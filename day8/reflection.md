# Day 8 Reflection

Designing TicketHub taught me that the hardest concept was cache invalidation. Redis makes seat lookups fast, but a cached “available” value becomes dangerous as soon as a reservation succeeds, expires, or fails. Every path that changes inventory must update or invalidate the corresponding key, and network delays can leave stale data. I learned to treat the cache as a performance hint, never the source of truth, and to let PostgreSQL constraints decide whether a seat is actually sold.

That lesson changed how I think about concurrency: the waiting room controls demand, Redis reduces contention, row locks serialize competing purchases, and a unique ticket constraint provides a safeguard. Feedback showed that I explained components but could connect user actions to data changes explicitly. I would improve by tracing a purchase end to end, labeling which service owns each decision, and stating failure behavior—what happens when payment succeeds but confirmation delivery is delayed. Clear diagrams should expose those boundaries.

My next steps are practical. I will build the API in Node.js, first implementing seat holds, idempotent purchase requests, and authorization tests. I will use PostgreSQL transactions and row-level locking, then test simultaneous requests to verify that one seat produces at most one ticket. Next I will containerize the API and database with Docker Compose, add health checks and migrations, and practice restoring data. Finally, I will instrument latency, queue depth, lock waits, and cache hit rates. These exercises will turn the design into measurable engineering decisions.
